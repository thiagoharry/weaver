\abstract{This article describes using literate programming the
  Weaver API. Weaver is a game engine and this API are how programmers
  interact with the engine in their game projects. Besides the API,
  this article also covers how the configuration file is interpreted
  and how game loops should be managed in a game project. The API is
  portable code which should work under OpenBSD, Linux, Windows and
  Web Assembly environments.}

\secao{1. Introduction}

\subsecao{1.1. File Organization}

When a user runs \monoespaco{weaver PROJECT} on the command line, a
new directory containing a Weaver project is created. Inside this
directory, the main loop is defined in the
file \monoespaco{src/game.c}, and inside it we find:

\alinhaverbatim
#include "game.h"

void main_loop(void){ // The game main loop
 LOOP_INIT: // Initialization code 

 LOOP_BODY: // Code executed each iteration
    if(W.keyboard[W_ANY])
        Wexit_loop();
 LOOP_END: // Code executed at finalization
    return;
}

int main(void){
  Winit(); // Initializes Weaver
  Wloop(main_loop); // Enter a new game loop
  return 0;
}
\alinhanormal

Inside \monoespaco{src/game.h}, we find:

\alinhaverbatim
#ifndef _game_h_
#define _game_h_

#include "weaver/weaver.h"
#include "includes.h"

struct _game_struct{
  // You can customise this structure declaring variables here.
  // But don't change it's name. And access it by its pointer: W.game
  int whatever; // <- This variable is here to prevent compiler errors
} _game;

void main_loop(void);

#endif
\alinhanormal

In this file, there is a struct that can be customized by the user and
used to declare global state variables. These variables are also saved
in the player's save file and sent over the network to inform clients
about the game state. This struct should be referenced via
the \monoespaco{W.game} variable. This implies that the API is
organized around a struct named \monoespaco{W}, which centralizes
access to all API resources.

The file \monoespaco{includes.h} is a simple header that includes all
other headers for user-defined modules (each module consisting of a C
source file and a corresponding header).

All API code must be either written directly in or included via macros
in the files \monoespaco{weaver.c} and \monoespaco{weaver.h}. The
structure of \monoespaco{weaver.h} is as follows:

\iniciocodigo
@(project/src/weaver/weaver.h@>=
#ifndef _weaver_h_
#define _weaver_h_
#ifdef __cplusplus
  extern "C" {
#endif
@<Include Headers (weaver.h)@>
@<Data Structures (weaver.h)@>
@<Function Declaration (weaver.h)@>
@<Extern Variables (weaver.h)@>
@<Macros (weaver.h)@>
#ifdef __cplusplus
  }
#endif
#endif
@
\fimcodigo

The text in red above represents code that has not yet been
defined. For example, in the ``Include Headers'' section, one might
include the header \monoespaco{sys/param.h} to check whether the
program is being compiled on a BSD-based system. However, Windows does
not have this header; on Windows, we would typically include windows.h
instead.

To handle such cases, we can use conditional inclusion to include
different headers depending on whether the code is being compiled on
Windows or another system, as shown below:

\iniciocodigo
@<Include Headers (weaver.h)@>=
#if !defined(_WIN32)
#include <sys/param.h>
#else
#include <windows.h>
#endif
@
\fimcodigo

We may also want to include additional headers at this point. For
example, the standard input/output header (\monoespaco{stdio.h}) and
the standard library header (\monoespaco{stdlib.h}). The
header \monoespaco{stdint.h} is useful for defining fixed-size integer
types, while \monoespaco{stdbool.h} allows us to declare and use
boolean variables:

\iniciocodigo
@<Include Headers (weaver.h)@>+=
#include <stdio.h>
#include <stdlib.h>
#include <stdint.h>
#include <stdbool.h>
@
\fimcodigo

We will also define here the general structure of
the \monoespaco{weaver.c} file from our API:

\iniciocodigo
@(project/src/weaver/weaver.c@>=

\fimcodigo

and \monoespaco{weaver.h}), showing the code that should be inserted
there. This is how our API will be defined.

\subsecao{1.2. The W Structure}

The main data structure we will define is a struct
named \monoespaco{W}. This structure essentially acts as a namespace
for our API’s public functions and variables. We can now begin
defining this structure:

\iniciocodigo
@<Data Structures (weaver.h)@>=
// This structure will contain all the variables and functions
// defined at Weaver API:
extern struct _weaver_struct{
  struct _game_struct *game;
  @<Variables Namespace@>
  @<Functions Namespace@>
} W;
@
\fimcodigo

In addition to \monoespaco{W.game}, the structure will contain other
variables. We will centralize all public functions of the API in this
structure. Only private functions---whose names start with an
underscore---and certain initialization and finalization routines will
be defined outside the W structure. In this way, we prevent global
namespace pollution.

We declare this namespace as a global variable:

\iniciocodigo
@<Global Variables (weaver.c)@>=
struct _weaver_struct W;
@
\fimcodigo

\subsecao{1.3. Initialization and Finalization Functions}

The initialization function is responsible for setting the initial
values of the W structure. For this reason, it is one of the few
functions defined outside our namespace:

\iniciocodigo
@<Function Declaration (weaver.h)@>=
void Winit(void);
@
\fimcodigo

\iniciocodigo
@<Defining API Functions (weaver.c)@>=
void Winit(void){
  W.game = &_game;
  @<Weaver API: Initialization@>
}
@
\fimcodigo

The finalization function should deallocate any remaining memory,
release all resources, and close the program, indicating whether
everything completed successfully. Note that memory deallocation
should be the last step in the finalization process.

\iniciocodigo
@<Function Declaration (weaver.h)@>=
void Wexit(void);
@
\fimcodigo

\iniciocodigo
@<Defining API Functions (weaver.c)@>=
void Wexit(void){
  @<Weaver API: Finalization@>
  @<Weaver API: Memory: Finalization@>
  exit(0);
}
@
\fimcodigo

\secao{2. Time Counting}

Weaver measures elapsed time in microseconds ($10^{-6}$ s) and uses at
least 64 bits to store the time count. In addition to the total
elapsed time since program initialization, we also track the time
difference between consecutive iterations of the main loop.

First, we need a place to store the last time measurement, which we
keep in a global variable. On Windows, we use
the \monoespaco{LARGE\_INTEGER} type to store large integers, while on
other systems we use the timeval structure for high-resolution
timekeeping.

Our timekeeping global variable is declared here:

\iniciocodigo
@<Extern Variables (weaver.h)@>=
#if defined(_WIN32)
extern LARGE_INTEGER _last_time;
#else
extern struct timeval _last_time;
#endif
@
\fimcodigo

And here:

\iniciocodigo
@<Global Variables (weaver.c)@>=
#if defined(_WIN32)
LARGE_INTEGER _last_time;
#else
struct timeval _last_time;
#endif
@
\fimcodigo

The header to use \monoespaco{struct timeval} variables is included
here:

\iniciocodigo
@<Include Headers (weaver.h)@>=
#if !defined(_WIN32)
#include <sys/time.h>
#endif
@
\fimcodigo

The idea is to always store the last time measurement in this
variable. It is initialized with the first time measurement during
program startup:

\iniciocodigo
@<Weaver API: Initialization@>=
#if defined(_WIN32)
QueryPerformanceCounter(&_last_time);
#else
gettimeofday(&_last_time, NULL);
#endif
@
\fimcodigo

After initialization, all subsequent updates to this variable will be
performed using the function below:

\iniciocodigo
@<Function Declaration (weaver.h)@>+=
unsigned long _update_time(void);
@
\fimcodigo

This function reads the current time and stores it in the variable. It
returns the difference, in microseconds, between the last two
measurements. On Unix systems, the time difference is computed using
the method recommended in the GNU C Library manual. This subtraction
method is more portable and works even if the \monoespaco{timeval}
elements are stored as unsigned integers. The downside is that the
resulting code is less clear and intuitive. The code is:

\iniciocodigo
@<Function Definition (weaver.c)@>=
#if !defined(_WIN32)
unsigned long _update_time(void){
  int nsec;
  unsigned long result;
  struct timeval _current_time;
  gettimeofday(&_current_time, NULL);
  // Performing the carry:
  if(_current_time.tv_usec < _last_time.tv_usec){
    nsec = (_last_time.tv_usec - _current_time.tv_usec) / 1000000 + 1;
    _last_time.tv_usec -= 1000000 * nsec;
    _last_time.tv_sec += nsec;
  }
  if(_current_time.tv_usec - _last_time.tv_usec > 1000000){
    nsec = (_current_time.tv_usec - _last_time.tv_usec) / 1000000;
    _last_time.tv_usec += 1000000 * nsec;
    _last_time.tv_sec -= nsec;
  }
  if(_current_time.tv_sec < _last_time.tv_sec){
    // Overflow
    result = (_current_time.tv_sec - _last_time.tv_sec) * (-1000000);
    // This is always positive:
    result += (_current_time.tv_usec - _last_time.tv_usec);
  }
  else{
    result = (_current_time.tv_sec - _last_time.tv_sec) * 1000000;
    result += (_current_time.tv_usec - _last_time.tv_usec);
  }
  _last_time.tv_sec = _current_time.tv_sec;
  _last_time.tv_usec = _current_time.tv_usec;
  return result;
}
#endif
@
\fimcodigo

On Windows systems, there is already a function that measures time in
microseconds. As a result, our implementation becomes much simpler:

\iniciocodigo
@<Function Definition (weaver.c)@>+=
#if defined(_WIN32)
unsigned long _update_time(void){
  LARGE_INTEGER prev;
  prev.QuadPart = _last_time.QuadPart;
  QueryPerformanceCounter(&_last_time);
  return (_last_time.QuadPart - prev.QuadPart);
}
#endif
@
\fimcodigo

\secao{3. The main loops.}

All games are structured around main loops. These are blocks of code
that iterate indefinitely until some condition causes the program to
either switch to another main loop or terminate.

As shown in the initial example in \monoespaco{game.c}, a main loop
should be declared as:

\alinhaverbatim
void nome\_do\_loop(void){
 LOOP\_INIT: // Code executed at initialization

 LOOP\_BODY: // Code executed in each iteration
    if(W.keyboard[W\_ANY])
        Wexit\_loop();
 LOOP\_END: // Code executed at finalization
    return;
}
\alinhanormal

Before understanding how to correctly enter a main loop, it is
important to explain how the loop itself is structured and
executed. It consists of three sections: initialization, execution,
and finalization. These sections are marked by labels written in
uppercase.

This structure is simple to interpret. The code above can be viewed
as:

\alinhaverbatim
void nome\_do\_loop(void){
  // LOOP\_INIT
  for(;;){
    // LOOP\_BODY
    if(W.keyboard[W\_ANY])
        Wexit\_loop();
  }
  // LOOP\_END
}
\alinhanormal

While this interpretation suits some contexts, it does not reflect how
the main loop code is actually executed or translated. We cannot run
an infinite loop in all environments without blocking the game
interface.

In WebAssembly environments, a game loop can be executed only if it is
correctly declared as such. These functions should not contain an
infinite loop; instead, they are called repeatedly.

Due to these differences, to write more portable code, the execution
of a main loop should be interpreted as:

\alinhaverbatim
for(;;)
  nome\_do\_loop();
\alinhanormal

Inside the main loop function, we do not include an explicit
loop. Instead, we decide which section of the function to execute
based on the inserted labels. These labels are actually macros
containing additional logic and use goto statements to determine the
section to run.

Because of this, we cannot declare variables inside the main loop's
initialization section. If we do, they will have the correct value
only during the first iteration but not in subsequent iterations. For
example, the following code may produce undefined behavior and might
not print anything on the screen:

\alinhaverbatim
// WRONG
void loop(void){
LOOP\_INIT:
  int var = 5;
LOOP\_BODY:
  if(var == 5)
    printf("var == 5\\n");
LOOP\_END:
}
\alinhanormal

However, the following code is correct and prints on the screen during
all iterations because the variable is declared outside the function:

\alinhaverbatim
// CORRECT
static int var;

void loop(void){
LOOP\_INIT:
  var = 5;
LOOP\_BODY:
  if(var == 5)
    printf("var == 5\\n");
LOOP\_END:
}
\alinhanormal

Another thing to consider is that, in fact, there isn't just one main
loop executing at any given time, but two. One loop runs at a fixed
frequency: the loop that handles physics and game logic. The other
main loop runs as fast as possible: the loop that renders graphics on
the screen.

Ideally, in each iteration of the physics and logic loop, we execute
one or more iterations of the rendering loop. This means we can render
at a higher frequency than the rate at which we move objects, detect
collisions, and read user input. In each iteration of the rendering
loop, we need to render different images; otherwise, there is no point
in running this loop faster than the physics loop. Therefore, in the
rendering loop, we also interpolate the objects’ positions based on
their current speed, acceleration, and position.

By ensuring that our game physics and logic always run at fixed
intervals, we guarantee the necessary determinism to synchronize games
over networks like the Internet. At the same time, rendering as fast
as possible with interpolation provides a smoother and more natural
experience.

For more details on how to implement this, see [Fiedler 2004]. Our
implementation will follow this reference, except that our code will
be much less explicit because it will be hidden behind macros without
explicit loops.

In the following subsections, we will define exactly what to include
in the macros used in every main loop.

\subsecao{3.1. Loop Initialization.}

This is what the macro \monoespaco{LOOP\_INIT} does:

First, it checks certain variables to determine whether the loop
should finish. If so, but resources such as images, videos, shaders,
or sounds are still being loaded, the function simply returns. If no
resources are being loaded but the finalization section has not yet
been executed, a \monoespaco{goto} is used to jump to the finalization
section. If no resources are being loaded and the finalization has
already run, the loop finally stops.

If the loop does not need to finish and this function is being called
for the first time, execution continues normally. Otherwise,
a \monoespaco{goto} is used to avoid executing the initialization
section more than once.

If the function reaches this point, it means we are running it for the
first time. At this moment, the variable \monoespaco{W.loop\_name} is
set to a string representing the name of the current main loop.

How do we know whether to keep executing the loop? We use a global
variable. Since there is only one main loop, no semaphore protection
is needed. Similarly, global variables are used to track whether this
is the first execution of the loop, whether we are at the beginning of
a loop, or if the finalization has already been executed. These
variables are declared in the header as follows:

\iniciocodigo
@<Extern Variables (weaver.h)@>+=
extern bool _running_loop, _loop_begin, _loop_finalized;
@
\fimcodigo

And in the main file:

\iniciocodigo
@<Global Variables (weaver.c)@>+=
bool _running_loop, _loop_begin, _loop_finalized;
@
\fimcodigo

We initialize them here:

\iniciocodigo
@<Weaver API: Initialization@>+=
_running_loop = false;
_loop_begin = false;
_loop_finalized = false;
@
\fimcodigo

Knowing whether we are still loading resources (usually reading files)
and the name of the current loop is useful not only for the engine’s
internal logic but also for the user. Knowing that files are still
loading allows displaying a loading screen. Knowing the current loop
name is useful for debugging and for loading different resources
depending on the loop. Because of this, both variables should be
declared in the |W| structure. The maximum loop name length that can
be stored is set by the macro \monoespaco{W\_MAX\_LOOP\_NAME}.

\iniciocodigo
@<Variables Namespace@>+=
// Inside W structure:
#if !defined(W_MAX_LOOP_NAME)
#define W_MAX_LOOP_NAME 64
#endif
unsigned pending_files;
char loop_name[W_MAX_LOOP_NAME];
@
\fimcodigo

During initialization we set these variables to 0 and |NULL|
respectivelly:

\iniciocodigo
@<Weaver API: Initialization@>+=
W.pending_files = 0;
W.loop_name[0] = '\0';
@
\fimcodigo

The function that exits the loop is:

\iniciocodigo
@<Function Declaration (weaver.h)@>+=
#if !defined(_MSC_VER)
void _exit_loop(void) __attribute__ ((noreturn));
#else
__declspec(noreturn) void _exit_loop(void);
#endif
@
\fimcodigo

However, we will not define it yet. As shown in the function signature
above, this is a function that never returns, as specified in the code
using notation compatible with GCC, Clang, and Visual Studio. This is
because when it exits, it either calls the previous main loop, which
itself never returns, or it terminates the program, depending on the
case.

After this explanation, we can finally define the loop initialization
macro:

\iniciocodigo
@<Macros (weaver.h)@>+=
#define LOOP_INIT                                                   \
  if(!_running_loop){                                               \
    if(W.pending_files)                                             \
      return;                                                       \
    if(!_loop_finalized){                                           \
      _loop_finalized = true;                                       \
      goto _LOOP_FINALIZATION;                                      \
    }                                                              \
    _exit_loop();                                                   \
  }                                                                 \
  if(!_loop_begin)                                                   \
    goto _END_LOOP_INITIALIZATION;                                   \
  snprintf(W.loop_name, W_MAX_LOOP_NAME, "%s", __func__);            \
  _BEGIN_LOOP_INITIALIZATION
@
\fimcodigo

We end with the identifier \monoespaco{\_BEGIN\_LOOP\_INITIALIZATION},
which is the actual label name used by this macro (remember, this
macro is always invoked as ``\monoespaco{LOOP\_INIT:}''---with the
trailing colon).

\subsecao{3.2. Loop Body.}    

This is what the macro \monoespaco{LOOP_BODY} does:

When this macro is executed, we set to false the flag indicating that
this is the first loop execution, thus preventing the initialization
from running again. Then, we place a \monoespaco{goto} statement after
an \monoespaco{if} condition that will never be true. This prevents
compiler warnings about unused labels when using the
label \monoespaco{\_BEGIN\_LOOP\_INITIALIZATION}. The
label \monoespaco{\_END\_LOOP\_INITIALIZATION} marks the actual
beginning of the loop body.

Next, we measure the elapsed time since the last loop iteration and
accumulate it. If this accumulator exceeds the expected interval
between executions of the physics and logic code, we run that
code. Otherwise, we skip it and jump to the finalization section,
where we simply render on the screen. If a significant amount of time
has passed since the last loop execution, this loop body code may run
multiple times.

The accumulator that determines whether we should run the physics and
logic code is called \monoespaco{\_lag}. It is a global variable:

\iniciocodigo
@<Extern Variables (weaver.h)@>+=
extern unsigned long _lag;
@
\fimcodigo

\iniciocodigo
@<Global Variables (weaver.c)@>+=
unsigned long _lag;
@
\fimcodigo

We initialize it here:

\iniciocodigo
@<Weaver API: Initialization@>+=
_lag = 0;
@
\fimcodigo

We will define some variables that can be read by the user to obtain
timing information. One of them (\monoespaco{W.t}) will store the
elapsed time in microseconds since the game initialization. Another
(\monoespaco{W.dt}) will hold the interval between executions of the
physics engine and game logic. Both variables need to be declared
inside the \monoespaco{W} struct:

\iniciocodigo
@<Variables Namespace@>+=
unsigned long long t;
unsigned long dt;
@
\fimcodigo

The first variable should obviously be initialized to zero. The second
should be initialized with the same value as the
macro \monoespaco{W\_TIMESTEP}, which can be defined by the user to
control the granularity of code execution in physics and logic. If
this macro is not defined, we assume 40000 microseconds. This ensures
a frequency of 25 Hz for the execution of the physics engine.

\iniciocodigo
@<Weaver API: Initialization@>+=
#if !defined(W_TIMESTEP)
#define W_TIMESTEP 40000
#endif
W.dt = W_TIMESTEP;
W.t = 0;
@
\fimcodigo

The code of physics engine and internal logic shall be encapsuled in a
function called \monoespaco{\_update}:

\iniciocodigo
@<Function Declaration (weaver.h)@>+=
void _update(void);
@
\fimcodigo

We will define later the content in the body of this function:

\iniciocodigo
@<Function Definition (weaver.c)@>+=
void _update(void){
  @<Code to execute every loop@>
}
@
\fimcodigo

With all these definitions in place, we can now define the macro that
marks the beginning of the main loop:

\iniciocodigo
@<Macros (weaver.h)@>+=
#define LOOP_BODY                                            \
  _loop_begin =  false;                                      \
  if(_loop_begin)                                            \
    goto _BEGIN_LOOP_INITIALIZATION;                         \
_END_LOOP_INITIALIZATION:                                    \
  _lag += _update_time();                                    \
  while(_lag >= W.dt){                                       \
    _update();                                               \
_LABEL_0
@
\fimcodigo

Notice that the previous macro opens a \monoespaco{while} loop but
doesn’t close it. It should be closed by the code inserted by our
macro which delimits the end of the loop body. This macro should also
decrement the variable \monoespaco{\_lag} to prevent an infinite loop.

\subsecao{3.3. Loop Finalization.}

This is what our macro \monoespaco{LOOP\_END} will do:

First, to ensure that the loop opened by the previous macro ends, we
decrement \monoespaco{\_lag} by the value of \monoespaco{W.dt}. Then,
we increment \monoespaco{W.t} by that amount of microseconds and close
the loop block. Outside the loop, we continue performing activities
not related to the physics engine and game logic. As these activities
typically involve rendering, we place them into a function
called \monoespaco{\_render}. Next, we return. After the return, we
place a \monoespaco{goto} to a label that will never be executed to
avoid compiler warnings. Finally, we add a label marking the beginning
of the finalization section.

The only new component here is the rendering function:

\iniciocodigo
@<Function Declaration (weaver.h)@>+=
void _render(void);
@
\fimcodigo

We will define later the body of this function:

\iniciocodigo
@<Function Definition (weaver.c)@>+=
void _render(void){
  @<Render Code@>
}
@
\fimcodigo

And now we define the macro \monoespaco{LOOP\_END}:

\iniciocodigo
@<Macros (weaver.h)@>+=
#define LOOP_END                                           \
    _lag -=  40000;                                        \
    W.t +=  40000;                                         \
  }                                                        \
  _render();                                               \
  return;                                                  \
  goto _LABEL_0;                                           \
_LOOP_FINALIZATION
@
\fimcodigo

\subsecao{3.4. Entering in a main loop.}

Frequently, we will change which main loop to execute during the
game. However, this does not always mean a complete substitution. Some
main loops run inside other main loops---for example, when entering a
configuration menu during the game, or when, in a classic turn-based
Japanese RPG, we enter the combat loop after a random encounter.

We can use a stack of main loops, where exiting the last main loop
returns us to the previous one in the stack.

There are two ways to enter a main loop: one using a function we will
call \monoespaco{Wloop}, and the other using a second
function, \monoespaco{Wsubloop}. The first substitutes one loop for
another and can only be done if there are no pending files being
loaded (usually, in this case, we are in a loading screen, but not
necessarily). We can ensure this using macro techniques:

\iniciocodigo
@<Function Declaration (weaver.h)@>+=
#if !defined(_MSC_VER)
void _Wloop(void (*f)(void)) __attribute__ ((noreturn));
void Wsubloop(void (*f)(void)) __attribute__ ((noreturn));
#else
__declspec(noreturn) void _Wloop(void (*f)(void));
__declspec(noreturn) void Wsubloop(void (*f)(void));
#endif
#define Wloop(a) ((W.pending_files)?(false):(_Wloop(a)))
@
\fimcodigo

The two functions to enter main loops will never return. We specified
this above using conventions from Clang, GCC, and Visual Studio.

We also need a stack of main loops, which will be stored as an array
of pointers to functions. The array will
have \monoespaco{W\_MAX\_SUBLOOP} positions. This macro can be
controlled by the user; if it is not defined, we will assume the value
3. In addition to the stack, we need a variable to store the depth of
the main loop stack: \monoespaco{\_number\_of\_loops}.

We declare these variables as follows:

\iniciocodigo
@<Extern Variables (weaver.h)@>+=
#if !defined(W_MAX_SUBLOOP)
#define W_MAX_SUBLOOP 3
#endif
extern int _number_of_loops;
extern void (*_loop_stack[W_MAX_SUBLOOP]) (void);
@
\fimcodigo

\iniciocodigo
@<Global Variables (weaver.c)@>+=
int _number_of_loops;
void (*_loop_stack[W_MAX_SUBLOOP]) (void);
@
\fimcodigo

We also initialize the counting of number of loops as zero:

\iniciocodigo
@<Weaver API: Initialization@>+=
_number_of_loops = 0;
@
\fimcodigo

Entering a main loop using \monoespaco{Wloop} means verifying whether
we are already inside a main loop. If we are, we cancel the previous
loop. Then, we load the next loop onto the stack and update the count
of main loops. We also update our time measurements and finally run
the loop. In WebAssembly running in web browsers, this means directly
calling the function that controls the program's main loop. In other
environments, we run the function inside a \monoespaco{while} loop:

\iniciocodigo
@<Function Definition (weaver.c)@>+=
void _Wloop(void (*f)(void)){
  if(_number_of_loops > 0){
    @<Cancel Main Loop@>
    @<Memory Adjustment when Canceling Main Loop@>
    _number_of_loops --;
  }
  @<Code Before Loop and Subloop@>
  @<Code before Loop, not Subloop@>
  @<Memory Adjustment Before Loop and Subloop@>
  _loop_stack[_number_of_loops] = f;
  _number_of_loops ++;
#if defined(__EMSCRIPTEN__)
  emscripten_set_main_loop(f, 0, 1);
#else
  while(1)
    f();
#endif
}
@
\fimcodigo

It is important to remember that when running in a WebAssembly
environment within a browser, we need to include the correct header
for this:

\iniciocodigo
@<Include Headers (weaver.h)@>+=
#if defined(__EMSCRIPTEN__)
#include <emscripten.h>
#endif
@
\fimcodigo

Canceling a main loop involves calling the following function, if we
are running in the WebAssembly environment:

\iniciocodigo
@<Cancel Main Loop@>=
#if defined(__EMSCRIPTEN__)
emscripten_cancel_main_loop();
#endif
@
\fimcodigo

Starting a new subloop is similar; however, we update our main loop
counter differently, since it must be incremented. We also need to
check for potential stack overflows:

\iniciocodigo
@<Function Definition (weaver.c)@>+=

    emscripten_cancel_main_loop();
#endif
  @<Code Before Loop and Subloop@>
  @<Code before Subloop, not Loop@>

\fimcodigo

Before entering a main loop, we must perform some necessary
updates. First, we set the \monoespaco{\_running\_loop} variable to
indicate that the game engine should run the current loop rather than
exit it. We also update a variable that marks whether we are at the
beginning of the loop and thus should run the initialization code, as
well as a variable indicating that the finalization code has not yet
been executed. These variables are essential to control the main loop
flow. Finally, we update our time measurement.

\iniciocodigo
@<Code Before Loop and Subloop@>=

_loop_begin = true;
_loop_finalized = false;
_update_time();
@
\fimcodigo

\subsecao{3.5. Exit from Main Loop.}

Since there are two functions to enter a main loop, there are also two
functions to exit. One of them exits the current main loop and returns
to the previous one in the stack, if it exists. The other exits all
main loops and terminates the program.

The function that exits all main loops has already been partially
defined; it is the \monoespaco{Wexit} function.

Exiting a main loop involves adjusting a global variable that
indicates whether the current loop should continue running or be
terminated:

\iniciocodigo
@<Macros (weaver.h)@>+=
#define Wexit_loop() (_running_loop = false)
@
\fimcodigo

If you look again at the code inserted by macros into the main loops,
you’ll notice that when this variable is set to false and there are no
pending files being loaded, the function \monoespaco{\_exit\_loop} is
called.

This function cancels the current main loop and checks whether there
is another loop in the stack. If none exists, the program exits. If
one exists, it re-runs the initialization code of that loop and
resumes its execution:

\iniciocodigo
@<Function Definition (weaver.c)@>+=
void _exit_loop(void){
  if(_number_of_loops <= 1){
    Wexit();
    exit(1); // This line prevents compiler warnings
  }
  else{
    @<Code after Exiting Subloop@>
    _number_of_loops --;
    @<Code Before Loop and Subloop@>
#if defined(__EMSCRIPTEN__)
    emscripten_cancel_main_loop();
    emscripten_set_main_loop(_loop_stack[_number_of_loops - 1], 0, 1);
#else
    while(1)
      _loop_stack[_number_of_loops - 1]();
#endif
  }
}
@
\fimcodigo

\secao{4. Memory Management}

Memory management in our engine is handled by a dedicated subsystem
with its own allocation and deallocation functions. Unlike traditional
memory management using functions like \monoespaco{malloc}
and \monoespaco{free}, our subsystem requires the programmer to
specify the maximum amount of memory that will be used.

The required memory limit will vary depending on the type of
project. A game designed for a video game console, for instance, may
allocate the entire available memory from the start. On the other
hand, a PC game might begin development with a small memory limit,
which is increased progressively as the project grows. Eventually,
this memory limit should reach a defined maximum, based on the target
specifications of consumer machines. At that point, developers are
expected to optimize the game to stay within the chosen memory budget.

The user must define the maximum memory size using
the \monoespaco{W\_MAX\_MEMORY} macro in the \monoespaco{conf/conf.h}
file. If this macro is not defined, a default value of 4 KiB is
used. This small value will eventually force developers to specify a
more appropriate value as their project evolves---except in the case of
very trivial applications.

\iniciocodigo
@<Macros (weaver.h)@>+=
#ifndef W_MAX_MEMORY
#define W_MAX_MEMORY 4096
#endif
@
\fimcodigo

The total amount of memory specified will be allocated during
initialization, and its address will be stored in the pointer shown
below:

\iniciocodigo
@<Static Variables (weaver.c)@>=
static void *memory_arena;
@
\fimcodigo

To use the functions from our memory subsystem, we include the header:

\iniciocodigo
@<Local Headers (weaver.c)@>=
#include "memory.h"
@
\fimcodigo

During initialization, we allocate all the memory required for the
entire execution of the project in our internal memory arena:

\iniciocodigo
@<Weaver API: Initialization@>+=
memory_arena = _Wcreate_arena(W_MAX_MEMORY);
@
\fimcodigo

During finalization, we free the memory allocated during
initialization, as well as any remaining temporary allocations. To do
this, we call the function \monoespaco{\_Wtrash}, which frees all
memory from the left (permanent, allocated at initialization) and
right (temporary) memory stacks by passing the arguments 0 and 1,
respectively:

\iniciocodigo
@<Weaver API: Memory: Finalization@>=
_Wtrash(memory_arena, 0);
_Wtrash(memory_arena, 1);
_Wdestroy_arena(memory_arena);
@
\fimcodigo

Before entering a main loop, we use the
function \monoespaco{\_Wmempoint}. This function saves the memory state
so that we can later return to it. This allows us to deallocate in one
step everything that was allocated during the main loop.

Saving the state requires knowing the correct memory byte alignment
for the current environment. Weaver retrieves this value from the
macro \monoespaco{W\_MEMORY\_ALIGNMENT}, which can be explicitly defined
in \monoespaco{conf/conf.h}. If not defined, the default value is the
size of an \monoespaco{unsigned long}, used as a reasonable guess.

\iniciocodigo
@<Macros (weaver.h)@>+=
#ifndef W_MEMORY_ALIGNMENT
#define W_MEMORY_ALIGNMENT (sizeof(unsigned long))
#endif
@
\fimcodigo

Given this, we can save the state in our memory---the left stack used
for more permanent allocations:

\iniciocodigo
@<Memory Adjustment Before Loop and Subloop@>=
_Wmempoint(memory_arena, W_MEMORY_ALIGNMENT, 0);
@
\fimcodigo

This means that when we exit this loop, we will restore the memory
state in the left stack to what it was before entering the loop:

\iniciocodigo
@<Memory Adjustment when Canceling Main Loop@>=
_Wtrash(memory_arena, 0);
@
\fimcodigo

This basically will be the garbage collector in our project. We will
now define a function for the user to perform memory allocations. All
permanent user allocations will be performed in the left stack using
the default byte alignment:

\iniciocodigo
@<Function Definition (weaver.c)@>+=
static void *_alloc(size_t size){
  return _Walloc(memory_arena, W_MEMORY_ALIGNMENT, 0, size);
}
@
\fimcodigo

For temporary allocations that do not need to persist beyond a single
iteration of our main loop, we can use the following function:

\iniciocodigo
@<Function Definition (weaver.c)@>+=
static void *_talloc(size_t size){
  return _Walloc(memory_arena, W_MEMORY_ALIGNMENT, 1, size);
}
@
\fimcodigo

We will declare function pointers for both functions in
the \monoespaco{W} struct, and these functions will be invoked
as \monoespaco{W.alloc()} and \monoespaco{W.talloc()}, respectively:

\iniciocodigo
@<Functions Namespace@>=
void *(*alloc)(size_t);
void *(*talloc)(size_t);
@
\fimcodigo

And these functions will be ready for use after the initialization:

\iniciocodigo
@<Weaver API: Initialization@>+=
W.alloc = _alloc;
W.talloc = _talloc;
@
\fimcodigo

Everything allocated with the permanent function will be kept while
the main loop in which the allocation occurred exists. Once the loop
ends, these allocations are automatically deallocated. Memory
allocated with the temporary function will only persist during the
current iteration of the main loop and will be deallocated afterward,
except when loading data from files, which requires keeping temporary
allocations for a longer period.

\iniciocodigo
@<Código a executar todo loop@>+=
if(W.pending_files == 0)
  _Wtrash(memory_arena, 1);
@
\fimcodigo

\secao{5. Random Number Generator}

First, we need to include the header for our pseudo-random number
generation subsystem:

\iniciocodigo
@<Local Headers (weaver.c)@>+=
#include "random.h"
@
\fimcodigo

Next we declare a ponter to our generator struct:

\iniciocodigo
@<Static Variables (weaver.c)@>+=
static struct _Wrng *rng;
@
\fimcodigo

If the user of this API passes a predefined seed via the
macro \monoespaco{W\_RNG\_SEED}, we will use that seed to initialize the
generator:

\iniciocodigo
@<Weaver API: Initialization@>+=
#if defined(W_RNG_SEED)
{
  uint64_t seed[] = W_RNG_SEED;
  rng = _Wcreate_rng(_alloc, sizeof(seed)/sizeof(uint64_t), seed);
}
#endif
@
\fimcodigo

If no predefined seed is provided, we generate a seed uniformly at
random. The seed consists of four random 64-bit numbers, which
provides sufficient entropy for any generator. Rather than using less
robust methods, such as seeding with the current time, our approach
aims to produce the most random and unpredictable seed possible, which
is expected to yield better-quality results. However, generating such
seeds may require access to underlying cryptographic APIs on some
systems.

On Linux systems, we can use the \monoespaco{getrandom()} syscall. The
first argument of its corresponding C function is a buffer to be
filled, the second specifies the size in bytes, and the third contains
flags to modify the default behavior. The function returns the number
of random bytes filled, which may be less than requested if
interrupted by a signal:

\iniciocodigo
@<Weaver API: Initialization@>+=
#if !defined(W_RNG_SEED) && defined(__linux__)
{
  ssize_t ret;
  uint64_t buffer[4];
  do{
    ret = getrandom(buffer, 4 * 8, 0);
  }while(ret != 4 * 8);
  rng = _Wcreate_rng(_alloc, 4, buffer);
}
#endif
@
\fimcodigo

This requires the following header:

\iniciocodigo
@<Local Headers (weaver.c)@>+=
#if !defined(W_RNG_SEED) && defined(__linux__)
#include <sys/random.h>
#endif
@
\fimcodigo

BSD-based systems, including macOS, can obtain initial random values
by using the function \monoespaco{arc4random\_buf}. This function is
already included in the standard library and is guaranteed not to
fail:

\iniciocodigo
@<Weaver API: Initialization@>+=
#if !defined(W_RNG_SEED) && defined(BSD)
{
  uint64_t buffer[4];
  arc4random_buf(buffer, 4 * 8);
  rng = _Wcreate_rng(_alloc, 4, buffer);
}
#endif
@
\fimcodigo

In Windows, secure cryptographic random number generators can be
accessed through the Cryptography API: Next Generation (CNG). To fill
our initial seed with an unpredictable value, we call the function
responsible for generating random numbers in this API. The first
argument is NULL because the last argument is a flag indicating that
the system-preferred RNG should be used; without this flag, the
preferred algorithm must be specified explicitly. The other arguments
are the buffer to be filled and its size.

The documentation does not list all possible failure modes for the
Windows cryptographic random number generator. Therefore, it is
unclear whether certain errors preventing its use are temporary (as in
Linux, where signals can cause the \monoespaco{getrandom} syscall to
fail) or permanent. To avoid infinite loops in case of failure, if the
buffer cannot be filled with a random seed after 16 attempts, the
operation is aborted. However, it is expected that this function
succeeds on the first try:

\iniciocodigo
@<Weaver API: Initialization@>+=
#if !defined(W_RNG_SEED) && defined(_WIN32)
{
  uint64_t buffer[4];
  NTSTATUS ret;
  int count = 0;
  do{
    ret = BCryptGenRandom(NULL, (unsigned char *) &buffer, 8 * 4,
                          BCRYPT_USE_SYSTEM_PREFERRED_RNG);
    count ++;
  } while(ret != 0 && count < 16);
  if(ret != 0){
    fprintf(stderr, "ERROR: I could not initialize the RNG.\n");
    exit(1);
  }
  rng = _Wcreate_rng(_alloc, 4, buffer);
}
#endif
@
\fimcodigo

To use WIndows CNG API we first need to include this header:

\iniciocodigo
@<Local Headers (weaver.c)@>+=
#if !defined(W_RNG_SEED) && defined(_WIN32)
#include <bcrypt.h>
#endif
@
\fimcodigo

If we are running WebAssembly code in a browser environment, to
initialize a seed with unpredictable values, we can execute JavaScript
code to access the browser's Crypto API. We can
use \monoespaco{EM\_ASM\_INT} to run JavaScript code and obtain a 32-bit
integer (as integers in Emscripten are always 32 bits). By combining
eight 32-bit numbers, we can compose four 64-bit numbers, similarly to
what is done in other environments:

\iniciocodigo
@<Weaver API: Initialization@>+=
#if !defined(W_RNG_SEED) && defined(__EMSCRIPTEN__)
{
  uint64_t buffer[4];
  int i;
  for(i = 0; i < 4; i ++){
    buffer[i] = EM_ASM_INT({
      var array = new Uint32Array(1);
      window.crypto.getRandomValues(array);
      return array[0];
    });
    buffer[i] = buffer[i] << 32;
    buffer[i] += EM_ASM_INT({
      var array = new Uint32Array(1);
      window.crypto.getRandomValues(array);
      return array[0];
    });
  }
  rng = _Wcreate_rng(_alloc, 4, buffer);
}
#endif
@
\fimcodigo

If the random number generator was initialized during Weaver
initialization, then it must be finalized during the cleanup
phase. The code is as follows:

\iniciocodigo
@<Weaver API: Finalization@>=
_Wdestroy_rng(NULL, rng);
@
\fimcodigo

Now we need a function to use the random number generator without
having to pass the generator as an argument. We can implement such a
function as follows:

\iniciocodigo
@<Function Definition (weaver.c)@>+=
static uint64_t _rand(void){
  return _Wrand(rng);
}
@
\fimcodigo

To allow usage of this function in our API, we declare a pointer to it
in our \monoespaco{W} struct:

\iniciocodigo
@<Functions Namespace@>+=

@
\fimcodigo

And the pointer is initialized here:

\iniciocodigo
@<Weaver API: Initialization@>+=

@
\fimcodigo

\secao{7. User Interface}

To use our user interface subsystem, we include the header:

\iniciocodigo
@<Include Headers (weaver.h)@>+=
#include "interface.h"
@
\fimcodigo

Before initializing our user interface API, we need to decide what
should be done before and after loading each interface resources (like
their texture). Recall that Weaver API must keep in
variable \monoespaco{W.pending\_files} the number of files and
resources that we are currently loading. Therefore, before loading a
new resource, this variable must be incremented and after loading, it
should be decremented. Doing this is important because ensures that we
will not exit a main loop before loading its resources, which prevents
errors where the loading threads keep writting and loading resources
in memory areas that were already freed and allocated to other game
loop.

As we expect that textures and resources could be loaded by threads,
we need a mutex to ensure that only one thread increment or decrement
the variable. We also want to forbid to have more than one thread
loading resources from files to avoid increasing too much the memory
consumption. For this we will need two mutex variables. We will store
them as static variables:

\iniciocodigo
@<Static Variables (weaver.c)@>+=
STATIC_MUTEX_DECLARATION(pending_files_mutex);
STATIC_MUTEX_DECLARATION(loading_files);
@
\fimcodigo

The mutex is initialized during the initialization:

\iniciocodigo
@<Weaver API: Initialization@>+=
MUTEX_INIT(&pending_files_mutex);
MUTEX_INIT(&loading_files);
@
\fimdodigo

And finalized in the cleaning stage:

\iniciocodigo
@<Weaver API: Finalization@>+=
MUTEX_DESTROY(&pending_files_mutex);

\fimcodigo

With these mutexes, we can declare functions to be executed before and
after each resource loading. These functions will use the mutexes to
ensure correct counting of loading resources and that only one thread
loads resources at a time while others wait. Additionally, before
loading, we save the state of the memory region in the right stack of
our memory manager (the area for temporary allocations), and after
loading, we restore the previous state, effectively deallocating any
temporary resources created during the loading process.

\iniciocodigo
@<Function Definition (weaver.c)@>+=
void before_loading_resources(void){
  MUTEX_WAIT(&pending_files_mutex);
  W.pending_files ++;
  MUTEX_SIGNAL(&pending_files_mutex);
  MUTEX_WAIT(&loading_files);
  _Wmempoint(memory_arena, W_MEMORY_ALIGNMENT, 1);
}
void after_loading_resources(void){
  _Wtrash(memory_arena, 1);
  MUTEX_SIGNAL(&loading_files);
  MUTEX_WAIT(&pending_files_mutex);
  W.pending_files --;
  MUTEX_SIGNAL(&pending_files_mutex);
}
@
\fimcodigo

Another necessary step is to save the list of active interfaces onto a
stack at the beginning of each main loop, while marking all existing
interfaces as inactive. When exiting a main loop, we should restore
the list of active interfaces to the last saved state from the stack
and then remove that state from the stack. This ensures that all
interfaces have a scope limited to the loop in which they were
created, and their allocation and deallocation will follow the same
order and logic as the main loop execution.

correct points. Before entering a new loop or subloop, we save the

To render and activate interfaces, we first need to create them. The
interface API expects that we pass to the creation function a path for
the shader source code and a file for the texture. Both parameters can
also be \monoespaco{NULL} to use the default shader or texture.

However, instead of requiring users to provide full file paths, Weaver
Engine expects only the filename. The file will then be loaded from
the appropriate directory. Shader source code files should be placed
in the \monoespaco{shader} directory, and image files for textures
should be in the \monoespaco{image} directory. Both directories will
be searched inside the path defined by the \monoespaco{W\_DATA\_DIR}
macro, if it is defined. Otherwise, they are searched in the current
directory. This macro is typically defined only when compiling the
game for installation.

Therefore, new interfaces will be created by the following function:

\iniciocodigo
@<Function Definition (weaver.c)@>+=
static struct user_interface *new_interface(char *shader, char *texture,
                                            float x, float y, float z,
                                            float width, float height){
  char path_shader[512], path_texture[512];
  int dir_len, shader_len, texture_len;
  if(shader != NULL){
    shader_len = strlen(shader);
    path_shader[0] = '.';
    path_shader[1] = '\0';
    dir_len = 1;
#if defined(W_DATA_DIR)
    dir_len = strlen(W_DATA_DIR);
    memcpy(path_shader, W_DATA_DIR, dir_len + 1);
#endif
    memcpy(&path_shader[dir_len], "/shaders/", 10);
    dir_len += 9;
    memcpy(&path_shader[dir_len], shader, shader_len + 1);
  }
  if(texture != NULL){
    texture_len = strlen(texture);
    path_texture[0] = '.';
    path_texture[1] = '\0';
    dir_len = 1;
#if defined(W_DATA_DIR)
    dir_len = strlen(W_DATA_DIR);
    memcpy(path_texture, W_DATA_DIR, dir_len + 1);
#endif
    memcpy(&path_texture[dir_len], "/image/", 8);
    dir_len += 7;
    memcpy(&path_texture[dir_len], texture, texture_len + 1);
  }  
  return _Wnew_interface((texture == NULL)?(NULL):(path_texture),
                         (shader == NULL)?(NULL):(path_shader),
                         x, y, z, width, height);
}
@
\fimcodigo
